## 代码层的阻塞

本地 bridge 的 AST/路径扫描发现 66 个顶层场景脚本、约 28 个包模块、23 个脚本硬编码本机用户目录。已有 runtime、几何、benchmark 等模块，但 orchestration 仍大量分布在一次性场景脚本中。

| 位置（本地工作区） | 具体问题 | 处理方向 |
|---|---|---|
| `scripts/panel_quality_pipeline.py` | 等整机所有 compute job 消失，并检查全部全局锁 | 按设备 UUID 与资源预算排队 |
| `runtime/preflight.py` 与训练脚本 | 多套全局 GPU 锁，语义重复 | 统一 lease 接口；迁移前尊重旧锁 |
| `scripts/run_panel_reference_consistency.py` | 三个候选串行，各自启动 Isaac | RTX 常驻 worker，场景版本与状态重置 |
| `scripts/enhance_difix.py` | 单模型逐帧执行，PNG 写入/哈希同步，每帧重写增长中的 progress JSON | 推理/写盘分离，进度追加或定期快照；需单独 profile IO 占比 |
| `scripts/run_panel_stop_mission.py` | 高频 `.cpu().numpy()` 与 JSON 序列化，潜在每步同步 | 保持物理/控制频率的情况下缓冲与批量采集 |
| `simready_bridge/core.py` | 简单 IO helper 与 NumPy/SciPy 几何耦合，固定 `.tmp` 名称 | 本 PR 拆出纯标准库 `artifacts.py`，唯一临时文件 |
| 两组场景脚本 | `validate_panel_rotaries.py`/`validate_panel_asset_batch.py` 的 `main`，两个 motion validator 的 `progress` 函数存在相同函数体 | 后续场景参数化，保留不同验证合同，先确认调用关系再删除 |

以上本地脚本多数尚未进入公共仓库。本 PR 先把可复用运行与验收边界带入仓库，没有声称所有旧脚本已经自动接上调度器。旧 `scene_bench` 与新 `benchmark` 暂时并存，迁移前也不应将不同 SSIM/验收定义合并成一个成绩。

## 本 PR 的可测收益

在固定合成任务上比较 1 路与 4 路并发，再重复同一 DAG 检查缓存；每次核对全部输出哈希。[完整结果](../benchmarks/scheduler_cpu_20261112.json)

这是四个场景、每场景四个有依赖阶段的 **CPU sleep/哈希 fixture**。它验证并发排程、依赖与缓存复用，不能推导真实 GPU 加速倍率。GPU 卡号测试使用假 UUID 验证调度环境与锁，没有占用真实 GPU。

当前自动测试覆盖：分支真正重叠执行、join 顺序、CPU 容量、跨进程设备锁、子进程继承锁、遗留锁阻塞、RTX 隔离声明、资源队列超时、任务超时及子进程清理、输入/种子/运行时/质量协议/依赖变化失效、缓存损坏拒绝、越界路径/符号链接拒绝、失败传播、并发原子写入，以及统一 benchmark 的故障和防绕过测试。

## 实际 GPU 优化怎么验收

1. 固定源数据、候选模型、相机、分辨率、物理步长、控制频率、种子、驱动/运行时与质量合同。
2. 对同一负载分别测冷启动和热启动；重建、渲染、物理与预览分开计时。记录显存、CPU、磁盘、GPU 利用率及时间线，不能只看总 GPU 利用率。
3. 优先试常驻模型、视角批次、模型张量复用、异步 IO 和资产局部重算。每次只修改一个主要变量；保留失败和 OOM。
4. 复用相同质量协议比较逐视角和最差 ROI、源资产一致性、时序、碰撞、接触及任务成功。不通过则回滚，不放宽门槛换取速度。
5. 以同质量下每小时验收通过场景数、p95 时延、每个通过场景成本作为生产指标，随后决定是否值得写 kernel 或上单场景多卡。

GPU 并行优先级是跨场景 > 同一场景的独立视角/资产 > 单一训练任务多卡。缺陷反馈闭环仍需串行依赖；一轮尚未产生观测结果时，不能把后续修复当作独立任务提前跑。
