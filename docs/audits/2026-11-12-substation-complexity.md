## 3. 渲染：不是 714 次轻量截图

代码：[render_panel_stop_mission.py](../../runs/substation_profile_20261112_v1/workspace/scripts/render_panel_stop_mission.py)，关键行 25–35、62–104。

每帧逻辑为：读取已验证的物理轨迹 → 写入 25 个机器人刚体和 1 个目标按钮的姿态 → 更新跟随相机 → 请求 RTX 子帧 → 读取 RGB → PIL 画 HUD → 原始 RGB 通过管道交给 FFmpeg。

渲染副本已禁用物理、刚体和关节，所以录制阶段没有再重复跑 14,264 个物理步。

工作量计算：

```text
输出像素 P = 1920 × 1080 = 2,073,600
主循环请求子帧 S_total = 16 + 713 × 2 = 1,442
名义输出像素×子帧 = P × S_total = 2,990,131,200
机器人及按钮 USD 姿态写入 = 714 × 26 = 18,564 次
送入编码器的 RGB24 = 714 × P × 3 = 4,441,651,200 bytes ≈ 4.14 GiB
```

姿态更新复杂度为 O(FB)，像素读取和编码至少要遍历 O(FP) 数据。渲染计算的结构模型为 `Σ_j S_j × P_internal,j × C_scene,j`，其中内部渲染分辨率、每像素采样/着色成本、反射、材质、降噪和场景更新成本未实测。

**29.90 亿是输出分辨率下的名义像素子帧规模，不是实测 GPU 像素数、射线数或 FLOPs。** Kit 的预热更新也不在 1,442 中；引擎可能有多个内部 pass。不能将它除以显卡 TFLOPS 预测运行时间。

B 轮 `rep.orchestrator.step` 累计 **391.2556 秒，平均 547.98 ms/输出帧**，约 1.825 输出帧/秒；加上其他工作后完整录制为 445.9938 秒。25 fps 是成片播放速度，不是实际录制吞吐。

三个完整视频累计为 2,142 输出帧、4,326 个请求子帧。这是当时 A/B/C 验证的工作量。常规交付可在回归策略允许时只录制一次完整验收视频；减少实验次数属于减少工作量，需与相同工作量下的加速分开记账。

代码检查发现两个实验陷阱：

- `--frames` 抽样模式给**每个选中帧 16 子帧和 12 次 app.update**；完整模式只有首帧这样做，后续通常是 2 子帧。不能测几张 `--frames` 截图再线性外推完整录制耗时。
- 不能直接把 `wait_for_render=False` 当作等价优化：官方说明此模式可能返回前一帧的图像/标注，当前 HUD、姿态和接触时间需要严格匹配。异步实现必须增加帧 ID 与完成队列。[Isaac Sim 6.1 Replicator 文档](https://docs.isaacsim.omniverse.nvidia.com/6.1.0/replicator_tutorials/tutorial_replicator_getting_started.html)

## 4. 物理步进：已有 GPU，但每 2 ms 模拟时间都要交付结果

代码：[run_panel_stop_mission.py](../../runs/substation_profile_20261112_v1/workspace/scripts/run_panel_stop_mission.py)，关键行 90–96、294–331、368–374。

每步逻辑为：推进控制目标 → 必要时检查下一段机械臂轨迹 → 设置 PD 力和重力补偿 → 执行 PhysX → 更新状态 → 计算按钮行程与接触力 → 判定任务状态与异常接触 → 记录日志。下一步依赖本步的机器人状态、力反馈和状态机结果。

已核实配置为 `cuda:0`，冻结 USD 的 `enableGPUDynamics=1`、`broadphaseType="GPU"`。本机 Isaac Lab 后端 `isaaclab_physx/physics/physx_manager.py:556` 的实际调用包含：

```python
physx_sim.simulate(sim.cfg.dt, 0.0)
physx_sim.fetch_results()
cls.invalidate_transforms()
```

B 轮主循环 `sim.step(render=False)` 累计 **181.5581 秒，平均 12.7284 ms/步**。每步推进 2 ms 仿真，所以仅该调用就消耗模拟时长的约 6.36 倍；物理 worker 全过程为 297.7482 秒。

复杂度应按以下结构理解，而不是声称对 500 个形状每步进行全体两两精确碰撞：

```text
T ≈ N × [宽阶段筛选成本 + 候选碰撞对 K 的窄阶段成本
         + 求解迭代 I × 活跃约束行 C 的成本 + 调度/同步成本]
```

N 已知；每步 K、C、活跃刚体数、约束岛分布和 GPU kernel 时间未知。机器人配置了位置求解迭代 24、速度迭代 8，这不等于整个场景的统一 32 次迭代，也不能由 194 个关节直接推算全部约束行。`25×416` 是应用层接触观测矩阵，**不是 PhysX 窄阶段实际测试了同样数量的碰撞对**。

这里能做的是减少每步的宿主调度、重复状态更新和同步，检查无关渲染更新，并分析引擎宽阶段、接触与求解的占比。相邻闭环物理步不能像独立图片一样直接并行；多场景任务更适合独立环境并行。增大 dt、降低碰撞检查频率、删掉柜体碰撞或降低求解精度会改变基准语义，需另列质量折中实验。

## 5. 接触检查与 CPU 往返：复杂度和确定的重复逻辑

runner 行 324–331 每步读取一个 `(25, 416, 3)` 矩阵，按传感器顺序重排，计算每个向量的范数，屏蔽允许的脚—地面和末端—目标接触，取其余接触力的最大值。

```text
每步接触对 = 25 × 416 = 10,400
总向量范数 = 14,264 × 10,400 = 148,345,600
总输入标量 = 上述数量 × 3 = 445,036,800
按 float32 估算的一遍稠密数据量 = 1,780,147,200 bytes ≈ 1.66 GiB
3D 范数的标量工作模型 = 约 741,728,000 次乘/加 + 148,345,600 次平方根
```

时间复杂度 **O(NBA)**，单步中间矩阵空间复杂度 O(BA)。上述乘加是数学工作量估算，不是测得的机器指令；矩阵重排、平方、归约还会产生额外内存访问。GB10 为统一内存，1.66 GiB 不能称为实测 PCIe 传输量；float32 是这里的字节估算假设。

确定可改的代码：

| 位置 | 当前重复工作 | 改法与边界 |
|---|---|---|
| 行 326–327 | 每步重建脚索引和地面列；地面路径比较共 5,933,824 次 | 场景固定后在循环外建立索引和掩码；保持完整接触覆盖 |
| 行 330 | 每步在 416 个 actor 中查找目标索引 | 提前求目标列；不把每步检查缩减为只检查目标 |
| 行 324–331 | 整块矩阵回 CPU，重排后做 norm/mask/max | 在 GPU 保留矩阵和掩码，归约后只回传异常最大力、脚接触证据等必要量；先用现成张量运算评估，再决定是否融合 kernel |
| 行 307–309 | 重力补偿 GPU → CPU → GPU | 控制所需的 6 维力矩保留在 GPU；日志字段随状态快照一次回传，保留当前最后 19 个关节分量的切片语义 |
| 行 239、312、334、357、362 | 多次读取根状态、关节位置/速度 | 分别缓存 step 前和 step 后的快照；不能把跨物理步的两次读取误合并 |
| 行 294、303 | 机械臂目标每步 GPU → NumPy 限速 → GPU | 将目标推进留在同一设备；检查限速与轨迹插值的数值等价性 |

B 轮 `cpu()` 共 **198,867 次，平均 71.08 μs/次**，累计 **14.1351 秒**。这约占该轮物理 worker 的 4.75%，占该轮物理+审计+录制之和的 1.89%。只把这个已计时区间降为零、其余时序不变，直接归属收益也只有 14.14 秒；不是把 56 分钟大幅压缩的充分条件。

还要保留原有语义：对每个 body/actor 的力向量先取模，再取最大值，不能先把不同 actor 的力相加，以免相互抵消。GPU 减少回传有价值，但减少回传频率而漏检瞬时力峰值不是等价优化。

## 6. CPU 规划器：发现冗余，但尚不能归因几十秒

代码：[arm_planner.py](../../runs/substation_profile_20261112_v1/workspace/simready_bridge/runtime/arm_planner.py)，行 71–152；[kinematics.py](../../runs/substation_profile_20261112_v1/workspace/simready_bridge/runtime/kinematics.py)，行 65–98。

每个有效关节状态的包围盒检查为：

```text
O(J + M×E + M×L + M²)
J=6，M=12，E=465，L=23
环境包围盒比较 = 12×465 = 5,580 对/状态
固定机器人形状比较 = 253 对/状态（扣除挂载区域跳过项）
非相邻机械臂形状比较 = 42 对/状态（扣除已声明装配排除项）
```

已存储的成功离线路径包含 311 个状态样本；889 次在线 segment 检查每次至少 2 个样本，因此至少有 **2,089 次状态检查、11,656,620 对环境包围盒测试**。失败候选的中间检查没有完整保存在成功计划中，实际数量更高，不能伪造精确总数。

代码发现：

- `link_poses` 每次都对固定的 6 个 child frame 求逆；`check()` 又分别计算世界系和基座系 FK，使这里至少发生 **25,068 次本可缓存的固定 4×4 矩阵求逆**。`Chain.fk()` 内也有相同问题。
- 同一 q 的 FK 计算两遍；可缓存局部链变换再组合世界变换，但改运算顺序需验证数值差异。
- 环境包围盒每次全扫描。静态空间索引可以先筛选保守候选；平均工作量可下降，最坏情况仍可能全扫描，不能漏掉原来的 clearance 邻近对。
- `plan()` 的列表推导会把一个候选的所有 segment 都算完，即使前面已失败；可在保留诊断要求的前提下提前退出。

IK 使用 SciPy 有界非线性最小二乘，6 维变量、默认数值差分 Jacobian。用 I 表示实际迭代次数，残差/FK 评估部分可建模为 O(IJ²)，另有小型线性求解成本；实际 I 未记录。`max_nfev=300` 不能当成每次都执行 300 次，也不能从它推断精确 Jacobian 调用数。

现有 638 次 `solve_point` 累计 **4.0238 秒**，其中已包含部分 `body_frames`/`cpu()`。运动策略 ONNX 730 次仅 **0.1056 秒**。它们不是已证实的分钟级大头；planner 未有独立 span，不能把整个物理残余时间归到规划器。

## 7. 本次找到的 profiling 缺口

在插桩版中，Python 会先计算实参：

```python
cpu(environment_view.get_contact_force_matrix(dt))
# get_contact_force_matrix 执行完成后，才进入被装饰计时的 cpu()

cpu(robot.data.joint_pos)
# 如果属性读取触发惰性更新，这部分也在 cpu() 的计时范围外
```

所以 **14.1351 秒不包含全部状态读取成本**，只测到了 wrapper 内的转换、回传和等待。GPU 归约、合并 getter 的收益可能发生在其他区间，当前证据尚不能定量。

B 轮物理 worker 的粗粒度分解：

| 已分开的范围 | 秒 |
|---|---:|
| 主循环 sim.step | 181.5581 |
| cpu wrapper | 14.1351 |
| Kit 启动 | 10.5781 |
| 其余进程时间 | **91.4769** |
| 合计 | 297.7482 |

前三项在该插桩实现中没有相互嵌套；“其余”包含其他已计时工作、初始化/退出、状态 getter、规划、NumPy 接触归约、控制写入、Python 调度等。它不是“91 秒纯 CPU”，也不是“91 秒 GPU 空转”。其他细项如 `solve_point/body_frames/cpu` 存在嵌套，不能继续不加区分地相减。

渲染 worker 中所有已列 span 合计 416.9406 秒，其余为 **29.0532 秒**。例如 `np.asarray(im).tobytes()` 若作为计时函数的参数传入，会在管道写入 timer 之外执行；读取 JSON、构造场景、姿态更新、HUD 和退出也需单列。当前日志不能把这 29 秒逐项精确分配。

下一次 trace 应把 getter、设备计算、回传、规划、控制写入分成独立范围，并区分 CPU 发射、GPU 执行与等待；不能仅在宿主函数外套一个时钟后称其为 kernel profiling。

## 8. 优化顺序与收益口径

1. **优先定位 391 秒渲染调用和 182 秒物理调用。** 用固定输入的 Nsight Systems / 引擎 timeline 分解 CPU/GPU 关键路径，补上 getter 和 planner 的时间范围。当前只有 host span，尚无 kernel 级归因。
2. **先改确定冗余。** 缓存索引、固定矩阵逆、同一步状态快照；消除重力补偿往返；将接触 norm/mask/max 移到设备侧。每项独立记录质量、耗时和回退。
3. **检查渲染基础设施。** 核实实际创建的 render product/viewport、CPU 线程与 USD 更新成本，再评估批量更新/Fabric 路径；当前直接调用 `UsdGeom`，打开 Replicator 的 Fabric randomizer 开关不会自动改写这段代码。官方列出的 headless viewport 优化是待核查项，不能假定本运行已存在重复 viewport 渲染。[Isaac Sim 性能手册](https://docs.isaacsim.omniverse.nvidia.com/6.1.0/reference_material/sim_performance_optimization_handbook.html)
4. **按场景并行，再考虑视频切片。** 独立场景适合多个受控 worker；同场景物理需要时序反馈。视频切片需处理时域降噪预热和片段边界，并做图像等价性验收。单 GB10 上盲目多开 Isaac 可能争用资源，不能视为免费并行。

仅用于判断投入优先级的条件算术，基于 B 轮核心阶段之和 747.1631 秒，假设其他耗时完全不变：

| 假设 | 单轮节省 | 核心阶段合计 |
|---|---:|---:|
| cpu wrapper 成本降为零 | 14.14 s | 733.03 s |
| 渲染 step 的 host 成本减半 | 195.63 s | 551.54 s |
| 物理 step 的 host 成本减半 | 90.78 s | 656.38 s |
| 渲染和物理 step 的 host 成本均减半 | 286.41 s | 460.76 s |

这些是条件估算，不是目标承诺、实测提速或已经证明能达到的 kernel 优化幅度。减少分辨率、子帧或物理步数要另建质量—速度曲线；保持原质量的优化继续遵守基准中的物理轨迹、接触事件和图像验收要求。
